# ADR-0002: Клієнтські запити Valgrind (`fpvalgrind`) та умовна компіляція `-dFPC_VALGRIND`

- Статус: прийнято
- Дата: 2026-10-18

## Контекст
Інструменти пошуку гонок даних Valgrind (`helgrind` та `drd`) автоматично перехоплюють лише примітиви `pthread_*`. Натомість `System.Threading` та `SyncObjs` активно використовують користувацьку синхронізацію в просторі користувача:
- `TSpinLock` (атомарний цикл `InterlockedCompareExchange`);
- безблокувальну перевірку стану завершення задачі (`TTask.GetIsComplete`);
- перевикористання пам'яті об'єктів через `TThreadPool.TObjectCache` без виклику `FreeMem`/`GetMem`.

Без підказок для Valgrind прогін одного тесту `TParallel.For` породжував 600–1500 хибних попереджень (`possible data race`), унеможливлюючи пошук справжніх гонок даних.

## Рішення
1. Створено модуль `fpvalgrind` у пакеті `fcl-base` (`packages/fcl-base/src/fpvalgrind.pp`), який реалізує стандартний механізм клієнтських запитів Valgrind для `x86_64` (System V ABI) без зовнішніх залежностей від C-бібліотек:
   - `VgHappensBefore` / `VgHappensAfter` / `VgForgetAll`
   - `VgCleanMemory`
   - `VgBenignRace`
   - `VgRunningOnValgrind`
2. На інших архітектурах та ОС ці процедури є порожніми заглушками (no-op), тому код залишається повністю переносним.
3. У системних модулях (`syncobjs.pp`, `system.threading.pp`) виклики `fpvalgrind` обрамлено умовною компіляцією `{$IFDEF FPC_VALGRIND}`, щоб звичайні (production) збірки не мали жодних додаткових інструкцій чи залежностей.

## Розглянуті альтернативи
- **Використання зовнішнього файлу придушення (`suppressions`) замість анотацій**: відхилено для `TSpinLock` і `TObjectCache`, оскільки придушення приховує *всі* звернення всередині робочих процедур, разом зі справжніми гонками в коді користувача. Файл `fpc-helgrind.supp` залишено лише для специфічної поведінки RTL (`CDoneCriticalSection`).
- **Постійне ввімкнення клієнтських запитів без `{$IFDEF FPC_VALGRIND}`**: відхилено для гарячих шляхів (`TSpinLock.Enter`/`Exit`), де навіть кілька асемблерних інструкцій змінюють інлайнінг і продуктивність.

## Наслідки
- Кількість попереджень `helgrind` у `System.Threading` зменшено з ~1500 до **0**, що дозволило виявити й виправити реальні помилки синхронізації (`TTask.GetIsComplete`, `WaitForAny`, `StopCPUStats`, `ReapFinishedThreads`).
- Розробники прикладних програм можуть використовувати `fpvalgrind` для анотування власних безблокувальних структур даних.
